# 项目时间线 v1 开发规范

> 状态：开发前基线。此文件记录实现边界，不包含可直接复制的伪代码或过时演示数据。
>
> 业务规则以[需求文档与产品设计方案](./需求文档与产品设计方案.md)为准，HTTP 路径与请求响应以[接口设计](./接口设计.md)为准，表和字段以[database.sql](./database.sql)为准。若三者不一致，先修订契约，再编码。

## 1. 目标与范围

面向 10 人以内团队，完成项目 → 模块 → 工作项 → 任务的进度管理，并提供时间线、人员负载、站内通知和周报。需求池、完整缺陷管理（v1 仅支持成员提缺陷并路由）、IM/邮件通知、子任务、多负责人不在 v1 范围。

静态页面见 [prototype](../prototype/index.html)。它用于确认交互与视觉，不是生产代码或数据源；其中的 2025-12-18 仅是演示日期。正式系统使用服务端业务时区的真实日期。开发和测试可以显式注入固定时钟，生产环境不得启用演示时钟。

## 2. 技术与工程边界

- 后端：Java 17、Spring Boot 3、Spring Security、MyBatis-Plus、MySQL 8；单体服务。
- 前端：Vue 3、TypeScript、Vite、Vue Router、Pinia；时间线先用 CSS/SVG 绘制。
- 认证：登录返回 JWT。密码仅保存 BCrypt 哈希；停用账号无法登录。服务端逐请求校验身份、全局角色、项目职务和资源归属，不能只依赖前端按钮隐藏。
- 首次管理员通过一次性本地初始化命令创建：仅在数据库没有 ADMIN 时运行，输入从环境变量或交互终端读取，写 BCrypt 哈希，不输出密码；生产环境没有默认账号。修改角色或停用后，已有 JWT 下一次请求也必须按数据库最新状态判定。
- Redis 不属于 v1 必需依赖。只有明确的性能或多实例需求出现后才引入。
- 计划目录：`backend/`、`frontend/`、`docs/`、`prototype/`。当前尚未创建应用工程；具体构建和测试命令在脚手架落地后记录到 [PLAN.md](../PLAN.md)，不能把尚未运行的命令记为已验证。
- 配置由环境变量提供数据库连接、JWT 密钥和业务时区。正式建表使用 `database.sql`；`demo_seed.sql` 仅用于本地/测试环境，生产环境必须用单独的管理员初始化流程。

## 3. 唯一数据契约

使用 `database.sql` 中的表名：`users`、`projects`、`project_members`、`modules`、`nodes`、`tasks`、`task_work_logs`、`node_logs`、`notifications`、`weekly_reports`、`project_stage_targets`、`attachments`、`task_notes`、`node_deliverables`、`module_change_requests`。

- `users.global_role`：`ADMIN`、`USER`、`VIEWER`；`active=0` 保留历史记录，但拒绝登录和新的指派。停用当前 PM 前必须完成 PM 转交。
- `project_members.project_role`：`PM`、`MEMBER`。每个项目恰有一位 PM，PM 必须是有效且非 VIEWER 的项目成员；项目创建与 PM 转交在事务内维护这个不变量。
- 模块负责人、工作项负责人和任务执行人分别由 `modules.owner_id`、`nodes.owner_id`、`tasks.assignee_id` 表示。创建时依次默认继承，可在项目中有效且非 VIEWER 的成员之间改派。
- 项目必须设置开始日期，最终完成日期允许为空。阶段性目标由 `project_stage_targets` 直接关联项目，目标日期位于项目范围内。阶段性目标可带四个可空指标列（`metric_name/metric_unit/metric_target/metric_current`）：四列全空即日期型里程碑；有指标时 `metric_target` 必须大于 0，达成度由 `ProgressRules.metricProgress` 在读取时派生，不落库、不参与工作项聚合。模块只承担功能拆分和负责人继承，不承载阶段日期。
- 工作项状态：`NOT_STARTED` → `IN_PROGRESS` → `DONE`；未完成工作项可转 `CANCELLED`。v1 不开放已完成/已取消工作项重新打开。
- 任务状态：`TODO`、`DOING`、`DONE`。任务与工作项的状态命名不同，不互相复用。
- 不在 `nodes` 中持久化 `overdue`。延期、临近、受阻分别返回独立标记；显示色的优先级不改变原始标记。
- `projects.status=ARCHIVED` 时仍可读取历史，但项目内业务写入返回冲突错误；PM/ADMIN 可恢复项目为 ACTIVE。

## 4. 核心业务规则

### 4.1 进度和日期

- 层级为项目 → 功能模块 → 工作项 → 任务；工作项另有**项目级工作项**（`nodes.module_id` 为空），承接跨模块的测试、维护、缺陷修复和上线保障。工作项类型 `type` 为 `FEATURE/TEST/MAINTENANCE/BUGFIX/OTHER`；任务类型 `kind` 为 `FEATURE/FIX/BUG/TEST/OTHER`，并可用 `related_node_id` 关联原工作项。
- 工作项进度不再手填，由任务完成率实时派生：已完成任务数 ÷ 任务总数（四舍五入，未全部完成时最高 99）；无任务的工作项按状态估算（未开始 0、进行中 50、已完成 100）；已完成工作项固定 100。完成工作项前必须先把该工作项的任务全部置为已完成，否则返回冲突；已完成/已取消工作项不能新增任务，任务状态也不能再变更。取消工作项下未完成的任务不计入人员负载与周报计划人天（已发生工时仍计入实际人天）。标记完成时写 `actual_end`；进入进行中时若 `actual_start` 为空则写当日。
- 模块进度只计算本模块所有未取消工作项进度的算术平均；项目进度计算全项目所有未取消工作项（含项目级工作项）进度的算术平均；无有效工作项时为 0。展示时四舍五入为整数，仍有工作项未完成时聚合值封顶 99，计算时不对模块平均值再平均。进度在读取时计算，不落库、不由负责人维护。
- `overdue = status ∈ {NOT_STARTED, IN_PROGRESS} 且 plan_end < today`。`near = 同样状态且 0 ≤ plan_end − today ≤ 3`。业务日期统一取服务端配置时区。工作项状态/日期变化后下一次读取立即反映新标记，跨过午夜也不依赖缓存刷新。
- 标记受阻必须填写原因。延期工作项必须显示原因待填提示；负责人提交原因后通知 PM 和模块负责人，同一接收人去重。重复提交是否再通知按内容变化判断。
- 任务除名称/描述/截止日/计划人天外，记录「任务情况」（当前进展、问题或背景）与「处理方式」（准备怎么处理或已采取措施）；创建写 `TASK_ADD`、编辑写 `TASK_UPDATE`。删除任务为物理删除，同一事务内删除进展记录与工时、软删除任务附件，写 `TASK_DELETE`；已完成/已取消工作项不能新增、编辑或删除任务。
- 进展记录（`task_notes`）是**命名的 Markdown 文件**：`title` 为记录名/`.md` 文件名（≤120 字，服务端补 `.md` 后缀并拒绝路径字符），`content` 为 Markdown（≤20000 字，`MEDIUMTEXT`）。每个任务可保存多份、只追加不覆盖。编辑区粘贴的图片/文件立即上传为 `TASK` 附件的 `TASK_RECORD` 分类，正文只保存 `attachment:{id}` 占位：前端渲染图片时用 Blob 内联展示（单张超过 20MB 不拉取，改为点击查看/下载；图片语法误用非图片附件时同样降级为文件链接），其他文件渲染成可点击超链接（走附件下载接口或原有预览），附件同时出现在「附件」页签。编辑区列出本次上传并可移除（删除该任务附件、同时去掉正文占位）；焦点在编辑区内时，预览态粘贴会自动切回编辑并插入；非文件拖放不拦截浏览器默认行为。服务端不解析 Markdown、不校验占位；软删除的附件显示为「附件已删除」。Markdown 渲染使用 `markdown-it` 的 `html:false`，禁止用户 HTML 进入 `v-html`。

### 4.2 工时、负载与周报

- `tasks.estimate_days` 是当前任务计划人天。任务累计实际人天由 `task_work_logs.days` 求和返回，不在任务表冗余存储；没有明细时返回 `null`，与 0 区分。
- 人员负载展示跨项目未完成任务数、进行中/延期工作项数、选定自然周内到期项数、全部未完成任务计划人天和该周到期任务计划人天；取消工作项下的任务不计入这些统计。v1 不用“全部未完成任务人天 ÷ 8”推导一周负载百分比，因为分子和分母时间范围不同。
- 周一至周日为自然周。完成工作项按 `actual_end` 归周；新增工作项/任务按 `created_at` 归周；下周到期工作项按下一自然周的 `plan_end` 和未完成状态筛选。
- 周报发布时冻结自动汇总快照与 PM 说明，历史已发布周报不随源数据变化。草稿可重算，发布操作须保证幂等。
- “本周实际人天”按工时明细 `work_date` 落在自然周内求和。本周计划人天为截止日落在同一周的任务 `estimate_days` 之和；两者是不同口径，周报标注清楚。一次更正或删除明细后，未发布草稿实时变化，已发布快照保持不变。

### 4.3 审计与通知

工作项状态、改期、受阻、延期原因、任务状态、逐日工时与工作项交付物的新增/编辑/删除写入日志，至少保留操作人、时间、动作和变更前后值。业务更新与对应日志、站内通知在一个数据库事务中完成。

通知接收人与触发时点遵循接口设计（7 类：延期原因、标记受阻、工作项完成、任务指派、周报发布、变更申请待审批、变更审批结果）；本人通知仅本人可读取和标记已读。写入口统一走 `NotificationService`，不要在各 Service 里直接 INSERT。VIEWER 可标记自己的通知已读，这不属于业务数据修改。

## 5. 权限与边界检查

| 操作 | ADMIN | VIEWER | PM | 模块负责人 | 工作项负责人 | 任务执行人 |
|---|---|---|---|---|---|---|
| 查看项目数据 | 全部 | 全部 | 本项目 | 所属项目 | 所属项目 | 所属项目 |
| 账号创建、停用、改角色 | 允许 | 拒绝 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| 项目与成员管理、周报发布 | 全部 | 拒绝 | 本项目 | 拒绝 | 拒绝 | 拒绝 |
| 模块管理 | 全部 | 拒绝 | 本项目 | 拒绝 | 拒绝 | 拒绝 |
| 工作项状态 | 全部 | 拒绝 | 本项目 | 本模块 | 本工作项 | 拒绝 |
| 项目级工作项（创建/编辑/取消） | 全部 | 拒绝 | 本项目 | 拒绝 | 本工作项 | 拒绝 |
| 提缺陷（落在原工作项或项目级 BUGFIX 工作项） | 全部 | 拒绝 | 本项目 | 本项目 | 本项目 | 本项目 |
| 工作项交付物清单（新增/编辑/删除） | 全部 | 拒绝 | 本项目 | 本模块 | 本工作项 | 拒绝 |
| 提交模块变更申请 | —（可直接改） | 拒绝 | —（可直接改） | 本模块外可提交 | 本模块外可提交 | 本模块外可提交 |
| 审批 / 撤回模块变更申请 | 审批全部 | 拒绝 | 审批本项目 | 拒绝 | 拒绝 | 只能撤回自己提交的 |
| 任务状态、实际人天 | 全部 | 拒绝 | 本项目 | 本模块 | 本工作项 | 本人任务 |

所有写操作先校验目标资源所属项目，再校验项目角色或资源负责人；成员、负责人、执行人的变更还要校验目标用户是该项目有效成员。删除含工作项的模块、移出当前 PM、移出仍承担责任的成员均应拒绝并返回可理解的错误。

## 6. 首个端到端切片与验收

先完成管理员/PM 登录 → 创建项目 → 加成员 → 建模块 → 建工作项 → 时间线显示进度与异常 → 更新工作项状态的最短路径。随后扩展任务、工时、负载、通知和周报。阶段、可观察验收与验证命令见 [PLAN.md](../PLAN.md)。

开发前必须完成：确定本周工时口径；让 `database.sql`、接口字段和本文件一致；区分演示种子数据与真实初始化。应用落地后用自动化检查覆盖状态机、权限隔离、日期边界、项目进度和周报归周，并用代表性浏览器路径验证 UI。
