# 项目时间线真实录入体验与修改建议

2026-11-05，以管理员身份通过 http://localhost:5173 的实际界面，将 txy 的开发成果与后续计划录入。评判标准是：能否准确记录事实、快速安排下一步、轻松修正错误，而不是页面上有多少功能。

这套系统能完成基本登记、分组、文件上传和交付状态流转，但现在的核心问题是：要求用户先把项目整理成符合系统表单的样子，才允许记录。现实里最常见的“先记下来、暂未排期、历史成果迁入、做到一半调整、误操作改回来”，都很难顺畅处理。建议先修这些基础流程，再谈视觉美化。

## 本次实际完成的工作

创建项目 TXY / txy · 个人智能体（项目7），建立5个模块、6项已交付成果（工作项134–139），写入开发步骤和验收来源。完整13步计划上传到项目文档，其中07进行中、08–13待开发或补验；未编造未来截止日期。项目说明及周报草稿均解释了回填时间和100%统计范围。

管理系统的业务数据全部经网页提交，没有通过数据库、内部API或修改源代码来绕过界面。一次性验证草稿未提交，关闭后已丢失；没有留下额外测试工作项，没有删除旧项目，也没有发布周报。

## 应优先修复的问题

### P1 不能记录未排期工作，逼用户造日期

复现：项目概览 → 新建工作项，填写“07 状态动效与本地自动连接”、模块、负责人及说明，结束日期留空 → 创建。页面提示“请填写工作项名称、负责人和计划起止日期”，无法保存。实际上只有结束日期缺失，错误提示也没有定位到该字段。

影响：已知但未估时的工作不能进待办池；用户只能编截止日期或把任务塞进文档。前者制造假延期，后者让统计漏掉范围。这次真实录入就被迫选择了后者。

建议：工作项最小创建只要求标题，项目上下文自动继承；模块、负责人和日期允许待定。加入“待梳理/待排期”，排期与执行状态分开。进入承诺交付时再校验负责人、日期和验收条件。

验收：只有标题也能保存；未排期可筛选和批量安排，不参与延期计算；补全日期后自动进入时间线；错误直接标注缺失字段。

### P1 历史成果只能假装从今天开工，污染实际日期

复现：工作项134是11-02已有成果，创建后为“未开始”，编辑表单没有实际日期或历史完成入口；点击“开始工作”自动写实际开始11-05，确认交付又写11-05。135–139同样如此。周报的六项完成日期全部显示11-05。

影响：迁入既有项目后，周期、按时率和交付历史都不可信。用户只好在说明里反复解释。

建议：提供“录入已有成果”入口，允许选择初始状态及真实开始/完成日期；区分业务发生时间和记录时间；历史导入单独标记，通知可合并。原计划未知时保持未知，不能把实际验收日冒充原始承诺。

验收：回填11-03完成的成果，实际完成仍为11-03、审计时间为当天；周报按实际日期归属；无原计划的历史成果不被判为延期。

### P1 完成率对范围没有说明，容易制造项目已完成的错觉

复现：只有第一项成果交付时，即使多个模块为空，概览已显示“全部已交付”和100%。最终6项成果完成后，知识库与办公工具仍为0/0，项目说明明确还有7项进行中/待开发内容，概览和时间线仍显示“全部已交付”。

判断：这是“已登记工作项完成比例”，不是可证明的整个项目完成率。系统也无法理解写在文档里的范围；问题在于没有待办承载方式且指标命名过度概括。

建议：显示“已登记工作项 6/6 已交付”，同时显示待排期、未拆分模块和范围完整性。项目完成必须有明确收尾判断；如要展示总体进度，先约定范围和权重，不应默认按数量表示工作量。空模块显示“尚未拆分”，不要显示“已交付0/0”。

验收：存在未排期/未拆分范围时，不能出现无条件的“全部已交付”；每个百分比都能说明分母和统计对象。

### P1 未保存内容无保护，关窗即丢

复现：新建工作项填写标题、模块和说明，点击右上关闭；没有离开确认。重新打开标题、模块、说明全部为空。

影响：用户写完一段需求后一次误点就全部丢失，对耗时输入很不友好。

建议：脏表单离开提示“保留草稿/放弃”；自动保存项目内草稿，恢复时展示时间和标题；遮罩点击默认不关闭有内容的编辑框。

验收：关闭、Esc、切页、刷新四条路径均不会无提示丢失输入；草稿可恢复、可明确放弃。

### P1 完成交付后没有正常纠错入口

复现：工作项135交付后，页面提示“后续问题可继续报告和修复，无需重开功能”，主操作只剩报告Bug；编辑入口消失。

影响：误点完成、漏验收、标题笔误或补充说明，与交付后的新增Bug是不同问题。强迫所有情况都开Bug，并不能纠正项目状态。

建议：保留经权限控制的“重新打开”，填写原因并保留审计；说明/标题可修订留痕；状态操作后提供短时撤销。交付后的缺陷继续独立管理，二者都需要。

验收：管理员能恢复误交付项，交付统计与时间线同步更新，原始交付和撤销记录仍可追溯。

### P2 一项一页一循环，批量录入很低效

复现：创建按钮只有“创建并查看详情”。每项都要返回概览 → 新建 → 选模块 → 日期 → 展开说明 → 保存 → 开始 → 确认交付 → 再确认。6项成果重复走同一路径。工作项列表没看到批量选择、批量改状态或导入入口。

建议：增加“保存并继续”，继承模块等上下文；允许多行粘贴标题建草稿；列表支持行内负责人/状态/日期编辑，以及批量移动、排期和导入预览。历史成果用专用导入步骤，避免伪造状态流转。

验收：10项已有标题的待办可一次粘贴进入草稿；连续创建不会离开当前列表；批量操作有预览和失败明细。

### P2 分类选错后不能移动，正常整理成本过高

复现：工作项134的编辑表单中所属位置禁用，文字“已有工作项的所属位置保持不变”。

影响：项目初期分组不一定正确，后续拆模块、合模块是常见整理行为，不能要求删掉重建或永远留在错误位置。

建议：提供“移动到模块/项目级”，保留ID、进展、附件、Bug与历史；移动前说明权限和负责人变化。

验收：已存在工作项可移动，原链接不变，所有关联内容保留，两个模块统计同时更新。

### P2 交付要求开工就锁死，不允许合理变更

复现：工作项134进入进行中后，“交付资料”提示不能新增/删除要求，名称与负责人锁定；编辑弹窗仅允许状态、备注和关联文件。

影响：纠正错字、补充遗漏验收项、交接负责人都无法直接进行。严格冻结并不等于需求可追踪。

建议：交付要求版本化；进行中允许有原因的变更，展示前后差异。真正需要审批的范围变更单独审批，别把所有修改都禁止。

验收：能补充和修订要求；历史基线保留；评审者看得出何时、由谁、为什么修改。

### P2 文档只能上传，不能写计划；Markdown预览直接露源码

复现：文档页只有“上传项目文档”，点击后先切到项目级文档，还要再点“上传文件”才开表单。上传txy-progress-2026-11-05.md后预览，显示原始“#”“##”及表格竖线，没有渲染为标题和表格。

影响：整理一份计划要先离开系统生成文件，再上传；修改要重新生成上传。开发项目最常见的Markdown资料也不易阅读。

建议：文档入口提供“新建文档、添加链接、上传文件”；直接支持Markdown编辑/预览和版本记录；上传按钮一次就打开正确表单；代码块保留原样，文本安全渲染。

验收：在项目里直接写计划并保存；Markdown表格、标题、列表正常显示；能关联仓库路径或外部文档；不为改一行文字重复上传。

### P2 单人操作给自己发12条通知，而且通知不说是哪项工作

复现：本次6项创建和6项交付后，通知中心出现12条未读；卡片仅“工作项已指派/工作分派”或“工作项已完成/功能已交付”，没有项目和工作项名称。

影响：用户已知道自己刚做的操作，红点只增加噪声；真有别人分配任务时也无法直接判断哪项重要。

建议：默认不通知动作发起者；通知明确项目、工作项、操作者、变更和可操作入口；批量导入合并；按项目/类型筛选，系统信息与需处理事项分开。

验收：自己给自己创建/完成不会产生12条未读；别人指派的卡片一眼能看清是什么工作。

### P2 小项目界面承担了过多分类和重复结构

复现：项目级文档只有1个文件时仍展开八组、28个分类（绝大多数为0）；工作项列表每个模块单独重复表头，包括无工作项的知识库模块。阶段目标被放在“设置”第三个页签中维护。

影响：真正要看的工作和文件被空结构包围；安排下一步要在概览、模块、工作项、时间线和设置之间切换。

建议：默认只显示有内容/常用的分类，其他折叠；工作列表用一张紧凑表支持分组折叠；把目标放回计划/时间线就近维护；核心入口集中为概览、工作、计划、资料，设置只处理成员和规则。

验收：只有1个文件时不会被几十个空分类挤占；空模块可折叠；从计划页可直接创建/修改目标；10人以内团队默认不被复杂结构阻挡。

## 视觉层级与操作流程专项复核

2026-11-05补充。前述问题偏重业务规则，本节专门评估内容主次、提示、按钮、信息密度和操作路径。检查了当前窗口、1440×900桌面以及390×844窄屏；以下像素值来自页面加载稳定后的可见DOM布局量测。它们用于复现空间问题，不代表每台设备都具有同一数值。

整体判断：界面已经有基础的蓝色主按钮、白底次按钮和文字操作，不是完全没有样式规范；但信息摆放、强调程度和操作频率不匹配。页面更像把管理字段、使用说明和组件逐块排列，用户需要自己找出今天该处理什么。

### V01 首屏顺序错误，下一步排在统计和模块之后

桌面1440×900下，项目说明占119px，进度卡119px，基本信息卡102px，模块区382px；“需要处理”容器从y=994开始，标题在1019，首屏不可见。当前说明由本次体验录入，确实较长；这是内容长度和产品不做摘要共同造成的问题，不能全归咎于页面。

修改：标题行只留项目名、短状态、负责人和一个主操作；项目说明默认2行，可展开。首屏第一块为需处理事项和下一步，第二块是近期交付；项目背景和模块分布移到后面。

验收：1440×900首屏能看到待处理/下一步的真实条目或一句空状态；200字与1000字说明不会把主要操作推走。

### V02 同一件事反复说，文字很多但新增信息很少

概览同屏出现“全部已交付”“已过计划完成日5项：已交付5项”“全部6项已交付6项”“交付进度100%”。基本信息又显示“0项延期或受阻”，下面还有“当前没有延期或受阻工作项”。这些信息不是五件事，不应占五个视觉位置。

修改：主摘要收成“已登记交付6/6 · 待排期7 · 受阻0”，范围不完整时不展示整个项目已完成。完成比例只在一处显示。无风险压缩为一行，避免空卡片和大面积正常状态。

验收：每个指标有唯一主展示位置；正常状态不比异常状态更占空间。

### V03 规则说明常驻，页面像一份操作手册

创建表单长期显示“功能工作选择功能模块……”“默认带入模块负责人……”；交付资料连续展示约90字规则和另一条只读规则。已完成页面还常驻“后续问题……无需重开功能”提示条。前后出现“一条要求可关联文件”“在上方要求关联文件”等相近提醒。

修改：每条提示必须回答“现在看见它会改变哪个决定”。不会改变当前操作的说明移到字段旁帮助或首次引导；自动带入负责人直接表现为已填好的值，不每次解释算法；只读状态只在受限控件附近解释原因。必要风险与不可逆后果继续显式显示，不能一律藏起来。

验收：正常操作页最多一条上下文提示；同一规则不在标题下、正文和弹窗重复；错误紧邻出错字段并提供修正办法。

### V04 只有6项工作，却要滚约两屏浏览

1440px宽度下工作列表总高约1814px。第一项工作在y=514，第二项在768，第三项到1023；每个模块有独立卡片标题、负责人、表头及“新建工作项”，空模块还显示完整空表。页面总共6个“新建工作项”入口。

修改：采用一张紧凑表，模块是可折叠分组行，表头只出现一次；组内新增保留为轻量加号，页头一个主新增入口。默认折叠已完成和空分组，并提供展开全部。不靠把字体缩小来提高密度。

验收：桌面首屏至少看到6–8条正常工作记录；工作项行高约44–52px；分组标题约36–40px；筛选条件和表头易于返回。

### V05 表单把常用内容藏起来，却把解释摊开

“说明”和“交付要求”藏在“更多信息（类型、说明）”里，折叠标题甚至没有提到交付要求；常用说明要额外点开，而归属和负责人规则一直占位。展开后提交按钮稳定位置约y=1046，900px高的视口看不到，必须滚动；关闭按钮则一直在上方。

修改：默认展示标题、简短说明、模块和负责人；日期放在可选的“安排时间”；验收标准是独立折叠区。表单正文内部滚动，底部取消/保存固定可见。快速录入只保留最低字段，完善信息放在后续编辑。

验收：1440×900以及1366×768下，展开所有字段后保存和取消仍可见；输入区域滚动不带走提交栏；用户不必打开“更多”才能写清工作是什么。

### V06 主按钮颜色偏浅，文字对比不足

实测主要按钮为14px白字、#409EFF背景；同样的#409EFF用于白底工作项名称和文字操作。该组合相对白色的对比度约2.78:1，低于普通文字4.5:1常用可访问性要求。常见辅助灰#6B778C对白底约4.52:1，不应再通过降低透明度继续淡化。

修改：主操作和链接采用更深的统一蓝色，例如#2563EB（对白色约5.17:1）；正文、次要文字、占位文字分别定义颜色，不用浅色一味制造“轻”。状态颜色使用浅底深字，并配明确文字。

验收：正常字号的按钮/链接/正文对比至少4.5:1；焦点和悬停可辨认；状态不只靠颜色区分。

### V07 按钮语义和视觉层级不稳定

文档页顶部“上传项目文档”与卡片内“上传文件”同时使用实心蓝色；前者还只是切换页签，需要再点后者。概览里“新建模块”和“查看全部模块”都是有边框按钮，导航与写入动作没有充分区分。“查看与维护目标”同时混合查看和修改，读起来像系统术语。列表“延期0”仍红色，“受阻0”仍紫色，正常零值也在争夺注意力。

修改：一个操作区域只保留一个主按钮；次要动作描边，跳转用文字链接，低频操作进更多菜单。零风险使用中性色；有风险才强化。文案使用“新建工作项”“添加文件”“查看全部”“编辑目标”“保存”，避免“创建并查看详情”等把系统后续导航塞进动词。允许用户选择保存后继续新增或打开详情。

验收：一眼能分清主要提交、次要动作、导航和危险操作；相同动作跨页同名同样式；按钮点击结果符合文案。

### V08 文件与进展页暴露了太多存储细节

交付页连续出现“图纸、文档与实际文件”和“文档与文件”两个同级标题，文件区的标题直到y=834、878才出现。进展记录默认要求用户面对“进展记录-2026-11-05-1.md”“保存为.md”，然后是12个排版工具、编辑/源码切换和两段上传/保存规则。用户原本只想写一句今天做了什么，却先被要求理解文件式存储。项目文档虽然没有在线创建入口，工作项进展实际上已有编辑器，这种能力分布也不统一。

修改：交付页合成“验收清单”和“附件”两区；进展默认一个“更新进展”输入框，标题可自动生成，格式工具按需展开，源码放更多选项。文件名、版本格式等放详情。项目文档复用已有编辑能力，避免只允许上传。

验收：写一句进展只需输入后保存，不必处理.md文件名；上传和关联附件在相邻位置完成；同一区域不出现同义双标题。

### V09 小屏只是堆叠桌面元素，重要内容被挤到很下面

390×844下全局导航两行仍展开，项目页签又占一行，项目标题从y≈333才出现；当前长说明使主操作在y≈644，“需要处理”标题到y≈1972，页面高约2621。项目页签容器约343px、内容约372px，需要横向滚动。主要按钮高32px，部分文字按钮约19–28px，对触屏偏小。该页面没有整页横向溢出，问题主要是首屏占用和触控目标，不应误报为横向破版。

修改：全局导航收进抽屉，顶部只留返回/项目名/更多；项目页签只显示常用项，其余进入更多。移动端摘要默认收起，主操作与关键状态靠上；触控目标至少44×44px，列表改为简短可扫描条目。

验收：390×844首屏看得到项目名、状态、主要动作和至少一条当前工作；无需先滚过多层菜单与说明。

### V10 分类与导航过密，用户要反复判断该从哪个入口开始

项目级文档只有2个文件仍展开28个分类，许多0计数重复出现。概览、模块、工作项、时间线、设置都承载部分工作安排；阶段目标在设置里，上传有两个入口，交付资料还要跨“要求”和“文件”两区关联。虽然各页面各有用途，但默认入口没有围绕一个用户任务组织。

修改：主导航收敛为概览、工作、计划、资料；模块成为工作的分组方式，阶段目标放进计划页；设置集中放成员/权限/项目属性。分类默认显示有内容和最近使用项，其余折叠。创建工作、更新进展、补充附件尽量在列表右侧详情面板完成，返回保留筛选、滚动和分组状态。

验收：常见操作无需猜测三个近似入口；从列表打开详情再返回仍在原位置；2个文件不会让28个空分类占据主要视觉空间。

## 建议统一的界面规则

| 项目 | 建议基线 |
| --- | --- |
| 内容顺序 | 当前状态与待处理 → 下一步/近期交付 → 工作列表 → 项目背景与历史 |
| 主按钮 | 每个操作区1个；深蓝白字；桌面36px高，窄屏44px触控区；名称通常2–6字 |
| 次按钮与导航 | 次动作白底细边框；查看/跳转用文字链接；危险操作放更多菜单，临执行再明确后果 |
| 字号 | 页面标题24px、区块标题16–18px、正文14px、辅助12–13px；不让所有区块都像大标题 |
| 空间 | 4/8px间距节奏，常规卡片16–20px内边距；少嵌套卡片，避免为一句空状态创建大盒子 |
| 颜色 | 一个主色；红色仅真实错误/延期；黄色用于需要关注；绿色用于完成；零值与常态中性化 |
| 长文本 | 摘要2行；显式展开；原文始终可访问；列表不放整段验收解释 |
| 反馈 | 错误贴近字段；成功给短暂反馈；不可逆风险在操作前展示；帮助按需展开；不让多条toast叠成操作回放 |
| 列表 | 一套表头，可折叠分组，常用行内操作；低频动作进更多菜单 |
| 弹窗 | 标题固定、正文滚动、提交栏固定；长编辑可用侧栏/完整页，别无限加高居中弹窗 |

## 提示文字的删减示例

| 现有表达 | 建议处理 |
| --- | --- |
| 项目按模块划分功能，每个模块下安排小功能工作项 | 已有模块时删除；首次空状态用“按模块整理工作”并提供新增入口 |

| 工作项开始后只能更新……最多20条，每条200字以内 | 限制在编辑时就近说明；字数实时显示；操作前才解释变更影响 |

删除提示的前提是操作本身清楚；如果没有提示用户就无法理解字段，优先改字段、默认值和流程，而不是再写一段说明。

## 下一版的流程验收

新增待办：在工作列表输入标题 → 回车创建草稿。详细安排：打开侧栏 → 填负责人/日期/验收 → 保存并留在列表。更新进展：输入一句进展 → 保存。查看文件：点击文件标题 → 预览。添加附件：一次点击打开选择/拖拽区 → 上传。历史成果迁入：选择初始状态与实际日期 → 预览统计影响 → 保存。

用txy同一批内容复测：桌面首屏能找出下一步；6项工作不需要两屏以上才能扫描；完整表单提交栏始终可见；帮助文字默认不超过必要的上下文提示；主按钮只有一个明确重点。

## 可以保留的做法

模块负责人能自动带入工作项；项目结束日期可空；工作项提供说明、活动记录及Bug入口；交付要求不直接换算成功能进度；上传文件保存版本；周报明确草稿和发布快照。问题在于这些局部规则没有组成顺畅的工作过程。

## 建议的改造顺序

第一轮先修数据真实性与纠错：待排期、历史回填、统计口径、草稿保护和重新打开。这些不解决，仪表盘越漂亮越容易误导。

第二轮降低录入与调整成本：快速新增、保存并继续、多行导入、行内编辑、移动模块、交付要求修订。

第三轮改善回看和协作：原生文档/Markdown、通知去噪、分类收敛、目标在计划页维护。

建议用同一套实际验收题测试新版：将txy的6项历史成果、1项进行中工作、6项未排期工作录入；关闭后恢复草稿；移动一个工作项；纠正一次误交付；上传并阅读Markdown；检查通知。全程不编日期、不写数据库、不靠说明纠正系统统计，才能说明核心流程真正好用了。
