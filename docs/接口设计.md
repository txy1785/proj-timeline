## 1. 通用约定

- **Base URL**：`/api`
- **认证**：登录后返回 JWT，请求头 `Authorization: Bearer <token>`；`/api/auth/login` 除外
- **响应包**：`{ "code": 0, "msg": "ok", "data": ... }`；code≠0 为业务错误（4001 未登录、4003 无权限、4004 资源不存在）
- **分页**：列表接口统一 `?page=1&size=20`，返回 `{ list, total, page, size }`
- **权限模型**：ADMIN 可读写全部项目，VIEWER 可读取全部项目与周报，USER 只能读取自己加入的项目。业务写接口按项目职务和资源归属校验；VIEWER 仅可调用自己的通知已读接口。
- **日期**：业务日由服务端配置时区决定，默认 `Asia/Shanghai`；日期字段使用 `YYYY-MM-DD`，时间戳使用含偏移量的 ISO 8601。不得使用客户端本地日期决定延期。
- **写入约束**：创建/改派负责人时目标用户必须是该项目有效且非 VIEWER 的成员；非法状态流转、无效日期范围或负数人天返回业务错误。并发更新返回冲突错误或执行受影响行数检查。

2026-10-27 当前产品以工作项为最小交付单位；Bug独立跟踪，通用任务/工时接口保留历史兼容，默认流程不再拆任务。数据表和旧记录不重写。

## 3. 关键接口详情

### 3.1 POST /nodes/{id}/status（状态流转）

```json
// 请求
{ "status": "DONE", "expectedStatus": "IN_PROGRESS" }
// 服务端行为
1) 校验状态机：NOT_STARTED→IN_PROGRESS→DONE；非完成态可→CANCELLED
2) 在工作项行锁下检查可选 expectedStatus；不一致返回4090。若 DONE：由管理者确认交付，actual_end=业务今天、写 node_logs(COMPLETE)、发通知 NODE_DONE 给 PM；旧任务和资料数量不阻断完成
3) 若 IN_PROGRESS 且 actual_start 为空：actual_start=今天
4) 重算 overdue（见 4.1）
```

### 3.2 PUT /nodes/{id}/overdue-reason（延期原因）

```json
// 请求
{ "reason": "支付渠道资质审批超期……" }
// 服务端行为
1) 校验当前 overdue=true（工作项确已延期），否则 400
2) 保存 overdue_reason，写 node_logs(OVERDUE_REASON)
3) 通知 OVERDUE_ALERT → PM + 模块负责人（工作项负责人本人不重复）
```

### 3.3 GET /projects/{id}/reports?week=（周报自动生成）

服务端按 `node_logs`、`nodes/tasks` 和工时明细实时聚合预览；若该周已有草稿，实时重算自动部分并保留 PM 说明；若已发布，返回冻结快照。GET 不写数据库，预览可没有 report id；PM 首次保存说明或发布前先调用 #41 创建草稿。口径：
- **本周完成工作项**：`actual_end ∈ [week_start, week_end]`
- **延期/受阻工作项**：`overdue=1` 或 `blocked=1`（当前态）
- **下周到期工作项**：`plan_end ∈ (week_end, week_end+7]` 且未完成
- **本周新增**：`created_at ∈ [week_start, week_end]` 的工作项与任务
- **工时**：本周实际人天 = 项目任务工时明细中 `work_date ∈ [week_start, week_end]` 的 `days` 之和；本周计划人天 = 截止日落在同周的任务 `estimate_days` 之和（排除取消工作项下的任务）。任务详情的 `actualDays` 是该任务所有明细之和，无明细返回 `null`。

发布时在事务内保存当前汇总快照、改为 PUBLISHED 并通知成员；对同一 report 重试不得重复生成通知。历史接口只返回已发布周报。

### 3.4 逐日工时

`workDate` 为业务日期且不能晚于服务端业务今日，`days` 必须大于 0，允许 0.1 人天精度；同一任务、记录人、日期只保留一条。新增时记录人默认当前用户，只有管理范围内角色可代录且须明确传 `userId`。被改派任务的历史工时仍归原记录人。新增、更正和删除都写入包含操作人及前后值的 `node_logs`。更正或删除后，未发布周报的实时预览和任务累计立即更新。

### 3.5 文档与附件

- 归属：`ownerType=PROJECT|MODULE|NODE|TASK` + `ownerId`；`category` 必须是分类字典中的编码，跨类型使用报 4000。任务级分类为「任务交付物 / 参考资料 / 进展记录附件（`TASK_RECORD`）/ 其他任务文件」；进展记录里粘贴的文件一律落为 `TASK_RECORD` 的普通任务附件，记录正文只保存 `attachment:{id}` 占位，不重复存文件。
- 权限：项目级写操作限 PM/ADMIN；模块级限模块负责人/PM/ADMIN；工作项级限工作项负责人/模块负责人/PM/ADMIN；任务级限任务执行人及其上级（工作项负责人/模块负责人/PM/ADMIN）。删除限上传者本人或对应层级的负责人；读取统一按所属项目校验。
- 上传（multipart）：`ownerType`、`ownerId`、`category`、`title`（默认取文件名）、`remark`、`file`。单文件上限 50MB，扩展名白名单校验；`title` 最长 200 字，`remark` 最长 500 字。
- 汇总：`GET /projects/{projectId}/attachments` 返回该项目下全部未删除文件，每项含 `ownerType`、`ownerId`、`ownerName`（项目名/模块名/工作项名/任务名），工作项/任务级文件另带 `nodeId` 供打开正确详情，供项目文档页「全部文件」视图使用。
- 版本：同一归属下 `title` 相同则 `version` 自增，历史版本保留；`(owner_type, owner_id, title, version)` 唯一。已软删除的记录同样占用版本号，删除后重传同名文件会得到更高的版本号而不是重新从 1 开始。
- 内容类型：**由服务端按扩展名推导**，不采用客户端声明的 `Content-Type`。只有 `pdf/png/jpg/jpeg/gif/webp` 以 `inline` 返回，其余强制 `attachment` + `application/octet-stream`，并带 `X-Content-Type-Options: nosniff` 与 `Cache-Control: private, no-store`，避免上传内容在同源被当作页面执行。
- 删除为软删除（`deleted=1`），磁盘文件保留；软删除后按 id 访问返回 4004。删除模块时其模块级文档一并软删除（工作项当前不支持删除，工作项级文档只随工作项存在）。
- 在线预览不新增接口：前端用 #53 取回 Blob 后在浏览器内渲染（PDF 走浏览器阅读器，docx/xlsx 走前端库），因此服务端对非 PDF/图片类型仍保持 `attachment`，不必扩大内联渲染面。

### 3.6 任务状态与进展记录

- 任务状态只有三档：`TODO`（待完成）/ `DOING`（进行中）/ `DONE`（已完成），通过 #26 直接切换，不再要求录入工时；置为 `DONE` 时写 `done_at`，改回其它状态会清空。逐日工时的 4 个接口保留、历史数据不动，界面已不再调用。
- 任务补充两个说明字段：`situation`（任务情况：当前进展、问题或背景）与 `handling`（处理方式：准备怎么处理或已采取的措施），各限 2000 字，创建（#24）与编辑（#25）时填写，详情展示；创建写 `TASK_ADD`、编辑写 `TASK_UPDATE` 日志。
- 历史任务类型为FEATURE/FIX/TEST/OTHER；默认不再提供通用新建任务入口。兼容#24请求kind=BUG时转入同一reportBug流程，relatedNodeId缺省使用路径工作项，直接落到未取消的来源功能，默认指派给功能负责人；其他创建请求字段中的执行人/估算不覆盖报告Bug规则。#25禁止非BUG历史任务转换为BUG，返回4000；既有BUG的类型与关联不可编辑。列表和详情继续返回kind/relatedNodeId/relatedNodeName。
- 删除任务（#59）为物理删除：同事务删除task_notes/task_work_logs、TASK附件软删除、写TASK_DELETE；非BUG历史任务的父项关闭后禁止编辑/删除，BUG按来源独立处理。删除追溯减少未发布周报/实时负载里的历史实际人天；已发布JSON快照不受影响。
- 进展记录（#56–#58、#76）是**命名的 Markdown 文件**，一个任务可以保存多份：`title` 即 .md 文件名，`content` 为 Markdown 正文。同一任务保存多次得到多条记录，按时间倒序展示；记录带作者与创建时间，可通过 #76 **再编辑**（标题和正文），最后编辑人与时间记录为 `updated_by/updated_at`。编辑与删除限作者本人或管理者（**执行人不能修改/删除他人的记录**）；注意与附件删除口径的差异——本任务执行人可以删除该任务下的任意附件，因为附件按「任务」授权，而记录按「作者」授权。归档项目与 VIEWER 一律拒绝；来源工作项已取消时记录仍按原权限处理。
- 再编辑（#76）为**原地更新**，不新增记录：标题可选（未传/为空保留原记录名），正文必填，校验同 #57；成功后写 `updated_by/updated_at`；不写 `node_logs`（action 枚举没有记录事件），以最后编辑字段留痕。并发编辑按最后写入生效，不引入版本号冲突检查。
- 正文里的 `attachment:{id}` 指向**本任务未删除的附件**：前端渲染图片时按 #53 取回 Blob 内联展示，其他文件渲染为超链接，点击走 #53 下载或原有预览；附件被软删除或不属于本任务时显示「附件已删除」。服务端不解析 Markdown，也不校验占位是否存在（附件会在列表接口里单独返回）。编辑区「本次上传」的移除动作调用 #54 软删除该任务附件，并只在客户端去掉正文占位；已保存记录里的占位若附件被删，读取时显示「附件已删除」。
- 记录名按文件名规则校验：≤120 字，禁止 `\ / : * ? " < > |` 与控制字符，未以 `.md` 结尾时自动补后缀；正文 ≤20000 字、不能为空。旧版 2000 字纯文本记录保留，`title` 由迁移默认值补齐。
- 记录删除是**物理删除且不写 `node_logs`**（该表 `action` 枚举不含记录事件），即记录没有删除审计；如需留痕需另加枚举值。
- 任务列表额外返回 `noteCount`，用于在工作项详情显示记录条数。

### 3.7 关键响应字段与错误

- `GET /projects` 每项含 `id/name/code/status/planStart/planEnd/progress/stats`；`stats` 含 `total/done/inProgress/overdue/blocked/near`。VIEWER/ADMIN 返回全部项目，USER 仅返回已加入项目。
- `GET /projects/{id}/timeline` 返回项目级 `stageTargets`、模块及其工作项，以及**项目级工作项** `projectWorkItems`（`moduleId` 为空）。阶段目标含 `name/description/targetDate` 与可选的 `metricName/metricUnit/metricTarget/metricCurrent`，有指标时另含派生 `progress`（无指标时该字段省略）；每个工作项含 `type`、`status/progress/planStart/planEnd/owner` 和独立的 `flags: {overdue, near, blocked}`。
- `GET /nodes/{id}` 中任务含 `kind`、`relatedNodeId`、`relatedNodeName`、`estimateDays` 与 `actualDays`；后者由工时明细求和，无记录为 `null`。工作项自身另含 `type`、`moduleId`（项目级为空）、`moduleOwnerId`（模块负责人，项目级为空）、`projectStatus`（`ACTIVE`/`ARCHIVED`，用于归档只读判断）、`totalTasks`/`doneTasks`（兼容历史计数，不再作为功能进度或交付条件）、`deliverableTotal`/`deliverableProvided`（交付物总数与已提供数）与派生后的 `progress`；`deliverables` 为交付物清单数组。
- `GET /workload` 的 `week` 可传该周任意日期，服务端归一为周一至周日。只统计调用者可读取的项目：VIEWER/ADMIN 全部，USER 为已加入项目；取消工作项下的任务不计入未完成任务数、活跃计划人天与该周到期人天。响应返回归一化周范围、`activeEstimateDays`（所有未完成任务计划人天）和 `weekDueEstimateDays`（该周到期任务计划人天），不把两者混作一个负载百分比。
- `POST /projects/{id}/reports` 请求体为 `{weekStart: "YYYY-MM-DD"}`，必须是周一；同一项目/周重试返回同一草稿。已发布周不可再创建草稿。
- 未认证返回业务码 4001；无权限 4003；不存在 4004；状态冲突或重复创建返回 4090；字段校验失败返回 4000。HTTP 状态分别为 401、403、404、409、400。
- 归档项目可读，除 #46 恢复外的项目业务写入返回 4090；账号管理及个人通知已读不受该项目状态影响。

### 3.8 工作项交付物清单（#60–#63）

- 一个工作项可以有多条交付物，字段为 `name`（≤200 字）、`status`（`WANTED` 待提供 / `PROVIDED` 已提供）、`ownerId`（可空，须为项目内有效且非 VIEWER 成员）、`remark`（≤500 字）、`attachmentId`（可空）、`sortOrder`（可空，默认 0）。v1 没有拖拽重排入口，列表按 `sort_order, id` 升序，实际等于创建顺序。
- `attachmentId` 必须是**本工作项下未删除**的工作项级附件（`owner_type='NODE'` 且 `owner_id=工作项`）；文件仍走 #51–#54 的上传与下载，清单不新建文件体系。附件被软删除后清单仍保留，读取时返回 `attachmentDeleted=1`，前端标“已删除”。
- 写入权限与工作项级附件一致：工作项负责人 / 模块负责人 / PM / ADMIN；VIEWER 与归档项目只读。
- 工作项已完成或已取消时：`status` 仍可更新（补标已提供是常态），`name/ownerId/attachmentId/remark/sortOrder` 任一变化返回 4090；新增与删除直接返回 4090。若传入的新负责人或新关联文件本身无效（非项目成员 / 非本工作项文件），会先按参数校验返回 4000，两种情况都不会落库。
- 新增、更新、删除分别写 `node_logs` 的 `DELIVERABLE_ADD` / `DELIVERABLE_UPDATE` / `DELIVERABLE_DELETE`，`detail` 与前后值记录清单项 id、名称与状态，便于周报与审计回溯；未产生任何字段变化的更新直接返回当前行、不写日志。
- 删除清单项是**物理删除**，不删除关联文件；关联关系只由清单持有。
- 工作项详情（#15）与时间线（#7）额外返回 `deliverableTotal` / `deliverableProvided`，供“已提供 x/y”展示；清单**不参与**工作项进度计算，也不作为完成工作项的前置条件（v1 决定）。

### 3.9 阶段性目标量化指标（#47–#48）

- `metricName`（≤100 字）、`metricUnit`（≤20 字）、`metricTarget`、`metricCurrent` 四个字段**全空表示日期型里程碑**；一旦有任意一个非空，必须给出 `metricName` 与 `metricTarget > 0`，`metricCurrent` 缺省按 0 且不得为负。
- 编辑（#48）时：请求体**完全不出现**这四个字段 → 保留原指标（兼容旧前端缓存与第三方调用）；显式把四个字段都传 `null` → 清空指标，回到日期型里程碑。
- 响应额外返回 `progress`（0–100）：当前值 ÷ 目标值，四舍五入后夹在 0–100，超额完成按 100 显示。进度不落库，读取时由 `ProgressRules.metricProgress` 派生；没有指标时不返回该字段（全局 Jackson 配置省略 null）。
- 权限与日期规则不变：仅 PM/ADMIN 维护，目标日期必须落在项目日期范围内。
- 指标只挂在阶段性目标上，**不参与**项目/模块/工作项进度聚合，也不进入周报统计；不带周期、评分与对齐概念。

### 3.10 模块变更申请（#64–#67）

- 申请人：项目内**没有模块编辑权限**的成员（非 VIEWER）。PM、管理员或该模块负责人调用提交接口会返回 409——他们本就能直接改模块，没必要走审批。
- 同一模块同时只允许一个 `PENDING` 申请：服务层先查一次给出友好提示，数据库还有 `pending_module_id` 生成列 + 唯一键兜底并发。
- 申请内容按列存（`name`、`description`、`owner_id`），提交时校验名称 ≤100 字、负责人须为项目内有效且非 VIEWER 的成员（可省略，省略即保持当前负责人）；`reason` ≤500 字；与模块当前值完全一致时返回 4000。
- 审批（#66）：`approved=true` 时在同一事务内锁定申请行与模块行、重新校验负责人、更新模块并写审批结果；`approved=false` 必须给 `remark`（驳回原因会展示给申请人）。已处理的申请再审批返回 409。通过/驳回都会给申请人发 `CHANGE_REQUEST_DECIDED` 通知，提交时给 PM 发 `CHANGE_REQUEST_SUBMITTED`。
- 撤回（#67）：仅申请人本人、且仅 `PENDING` 状态；PM 撤回别人的申请返回 403。
- 列表（#64）：PM/ADMIN 看本项目全部申请，其他成员只看自己提交的；`status=PENDING` 只返回待审批。
- 归档项目：申请、审批、撤回一律返回 4090（`requireProjectActive`）；待审批申请会保留到项目恢复。前端在归档态隐藏通过/驳回/撤回按钮。

### 3.11 报告功能Bug（#68）

- 权限：有效项目成员（非VIEWER）或ADMIN。归档项目409，非成员/VIEWER403。
- 请求：name必填（≤200字），description/situation可选（各≤2000字），relatedNodeId必须选择同项目工作项。缺少/0返回4000，负数/跨项目4000，不存在4004；来源CANCELLED返回4090。
- 直接在关联工作项下创建kind=BUG记录（复用tasks表），执行人继承该工作项有效负责人。NOT_STARTED/IN_PROGRESS/DONE均可报告，不再查找或创建项目级BUGFIX池。
- 创建记录status=TODO、created_by=提交人、related_node_id=关联工作项；同事务写TASK_ADD日志并发TASK_ASSIGN。返回id及兼容routedNodeId/routedNodeName/routedModuleName。
- 记录包含originNodeId/originNodeName/originNodeStatus/originOwnerId/originModuleOwnerId。历史分流Bug优先关联同项目且仍存在的related来源；缺失或跨项目时回退存储node_id，relatedNodeName不泄露其他项目名称。非BUG任务的来源仍为存储工作项。
- GET /nodes/{id} 保留原tasks，新增bugs（按来源汇总）、bugCount/openBugCount/legacyTaskCount；旧分流Bug在原功能展示，nodeId仍是存储归属供原任务深链及附件读取。Bug修复不重开已交付功能。
- Bug内容/改派/删除由来源工作项负责人、来源模块负责人、PM/ADMIN管理；状态另允许执行人。来源DONE仍允许独立处理；来源CANCELLED拒绝内容和状态修改；记录/附件沿原职责处理，归档全部只读。Bug的kind及原始relatedNodeId不能通过编辑改写。
- 通用历史任务的已关闭父项仍保持内容/状态限制。旧通知/tasks路径保留；新功能不依赖新增通用子任务。用户退出项目后不能凭残留执行人字段读取资源。

- 项目 `stats.blocked` 仅统计 NOT_STARTED/IN_PROGRESS 工作项；关闭项保留受阻历史字段但不计当前风险。工作项详情另带 `projectName`，用于统一任务抽屉的所属项目提示。`stats.overdue/near` 继续由业务日历派生。

### 3.12 业务上下文与历史工作台任务（#69–#70）

- `GET /context` 返回 `{businessDate,timeZone,unreadCount}`。日期来自注入的 `Clock`，时区来自 `APP_TIME_ZONE`（默认 `Asia/Shanghai`）；未读数只统计当前账号未读通知。前端使用此日期判断“今天”，不以浏览器时间替代。
- `GET /workspace/tasks` 返回 `{list,total,page,size,businessDate,timeZone,counts:{open,doing,overdue,done}}`，在数据库内完成过滤、统计与分页，`page` 至少 1，`size` 限 1–100。
- 查询参数：`scope` 默认 `OPEN`；可选 `status=TODO|DOING|DONE`、`projectId`、`assigneeId`、`q`、`dueWeek=YYYY-MM-DD`、`legacyOnly=false`。`legacyOnly=true` 在分页、total及counts统计之前排除kind=BUG，供历史任务入口使用；默认false保持旧客户端兼容。省略执行人时仅查当前账号任务；显式指定执行人仍限制在当前账号可读项目内，不能因任务仍指派给本人而访问已退出项目的数据。ADMIN/VIEWER 的可读项目为全部项目，USER 为本人已加入的项目。
- `q` 去除首尾空格，限 200 字，按任务名、工作项名、项目名包含匹配；`%`、`_`、`!` 按普通字符搜索。显式请求无权读取的 `projectId` 返回 403/4003，项目不存在返回 404/4004；非法 scope/status、非正整数 ID 或超长查询返回 400/4000。

| scope | 列表范围 | 用途 |
|---|---|---|
| OPEN | 有效项目；父工作项为 NOT_STARTED/IN_PROGRESS；任务为 TODO/DOING | 我的待处理任务，默认范围 |
| DONE | 有效项目；父工作项未取消；任务为 DONE（包含已完成父工作项） | 已完成任务 |
| HISTORY | 可读项目中该执行人的全部任务，包含归档项目与已关闭工作项 | 主动查看历史，操作权限仍由写接口判断 |
| WORKLOAD | 可读项目中父工作项未取消的 TODO/DOING 任务，保留归档项目及历史已完成父工作项范围 | 与既有人员负载未完成任务数一致的展开 |
| WORKLOAD_PLAN | 可读项目中父工作项未取消、本周到期的全部状态任务，包含 DONE；必须指定 dueWeek | 本周计划人天展开，明细估算之和与 weekDueEstimateDays 一致 |

- `dueWeek` 仅允许在 `WORKLOAD/WORKLOAD_PLAN` 使用，按指定日期所在周一至周日包含两端筛选任务截止日。WORKLOAD 对应 `/workload` 的 `weekDueCount`（未完成），WORKLOAD_PLAN 对应 `weekDueEstimateDays`（包含已完成）；WORKLOAD_PLAN 缺少 dueWeek 或其他 scope 传入时返回 400/4000。`status` 在上述范围内进一步筛选，筛选矛盾时返回空列表。
- `counts` 在相同账号、执行人、可读项目、`projectId/q` 范围内先统计，再应用所选 scope/status，所以状态切换不会改变页头统计。默认 `open` 是有效项目中父工作项未关闭的未完成任务数；`doing` 为其中 DOING；`overdue` 为其中截止日在业务日之前；`done` 是有效项目中父工作项未取消的已完成任务数。WORKLOAD/WORKLOAD_PLAN 模式改用既有负载的未取消父工作项范围，并应用可选周筛选。
- 行保留 Task 字段，增加 `projectId/projectName/projectStatus`、`nodeName/nodeStatus`、`assigneeName`、`relatedNodeName`、`noteCount`、`overdue`。行的 `overdue` 只对有效项目、未关闭父工作项下的未完成任务成立，历史记录不会被标记成待办延期。
- 排序依次为逾期未完成、今日到期、未来到期、未设截止日、已完成，再按截止日及任务 ID 稳定排序。`total` 是全部筛选后的行数，不是当前页长度。

### 3.13 管理待办与负载工作项展开（#71–#72）

- `GET /workspace/management` 返回 `{nodes,requests,nodeTotal,requestTotal}`。VIEWER 返回空数组和零总数；USER/ADMIN 使用真实管理职责和当前账号的项目读取边界。
- `nodes` 仅含有效项目中未关闭且延期或受阻的工作项。USER 须为该工作项负责人、所属模块负责人或项目 PM，ADMIN 可管理全部；延期记录优先，再按计划完成日和 ID 排序。
- `requests` 仅含有效项目中当前账号可审批的 PENDING 模块变更申请，USER 须为项目 PM，ADMIN 可审批全部。按申请时间和 ID 排序；归档项目申请保留在项目历史中，不出现在管理待办。
- 两个数组各最多 100 条，`nodeTotal/requestTotal` 为过滤后的完整总数。调用方须在总数超出数组长度时提示范围或引导到项目处理，不能把截断当成“没有更多”。工作项行含 `projectName/projectStatus/moduleOwnerId` 及现有 `flags/progress`；申请行另含 `projectName/moduleName/moduleOwnerId/requesterName/ownerName`。
- `GET /workspace/work-items?ownerId=&scope=ACTIVE|OVERDUE&page=1&size=20` 返回 `{list,total,page,size}`。ownerId 省略时使用当前账号；scope 默认 ACTIVE。ACTIVE 为负责人名下 IN_PROGRESS 工作项，OVERDUE 为 NOT_STARTED/IN_PROGRESS 且计划完成日早于业务日的工作项。与既有 `/workload` 的 activeNodeCount/overdueNodeCount 保持一致，范围包含可读归档项目；USER 仍须为项目成员，单纯残留负责人字段不能扩大读取范围。行包含工作项字段、projectName/projectStatus、moduleName/moduleOwnerId、负责人名与 flags/progress，按计划完成日、ID 排序；页长限制与任务接口一致。
- `/workload` 数字和工时口径保持原规则。USER 的人员行仅返回本人及可读项目中的有效非 VIEWER 成员，避免展示无关项目人员姓名；ADMIN/VIEWER 仍可读取全部有效非 VIEWER 账号。可读范围内没有任务的成员仍返回零统计。

### 3.14 缺陷接收预判与模块直接编辑（#73、#13）

- `GET /projects/{id}/bug-routing?relatedNodeId=` 返回 `{canSubmit,nodeId?,nodeName?,ownerId?,ownerName?,message}`，权限与 #68 提交相同：有效项目成员（非 VIEWER）或 ADMIN；只读账号/非成员返回 403/4003，归档项目返回 409/4090。
- GET 与 POST 使用同一接收工作项解析方法，遵循 #3.11 直接关联功能工作项的规则。GET 不创建工作项、任务、日志或通知，也不获取写锁。无可接收工作项、或接收负责人已失效时返回 HTTP 200、`canSubmit=false` 和原因；成功时返回工作项与负责人信息。
- 关联工作项不存在返回404/4004，跨项目或负数400/4000；GET省略或0返回canSubmit=false并提示选择功能。POST缺少关联4000；提交时在同一事务内重新锁定并检查，来源DONE仍可提交，CANCELLED返回4090，负责人失效4000。
- `PUT /modules/{id}` 接受名称、描述和负责人。当前模块负责人可直接修改这三项，不能调整 sortOrder；传入未变化的 sortOrder 兼容旧表单。PM/ADMIN 保留全部编辑权限，创建、删除、排序仍仅限 PM/ADMIN。转交负责人后，原负责人下一次编辑会被拒绝；服务端在模块行锁内重新核对当前负责人。VIEWER 和归档项目仍分别返回 403/4003 与 409/4090。
- 本轮功能交付模型调整更新进度与Bug来源权限，不修改数据库结构或既有记录。任务分派通知深链增加 `?task=<id>`，周报发布通知深链增加 `?week=<周一日期>`；旧通知地址仍可打开原页面。

### 3.15 功能交付与Bug工作台（#74—#75）

- 两个接口都返回 `{list,total,page,size,businessDate,timeZone,counts:{open,doing,overdue,done}}`。page≥1、size限制1—100，SQL内完成过滤/统计/分页；业务日由Clock与APP_TIME_ZONE提供。counts先于scope/status统计，保留projectId/q/人员/自然周/overdue筛选。
- deliveries参数：scope=OPEN|DONE|HISTORY（默认OPEN）、status=NOT_STARTED|IN_PROGRESS|DONE|CANCELLED、ownerId（默认本人）、projectId、q、dueWeek=YYYY-MM-DD、overdue=false、page、size。OPEN仅有效项目未开始/进行中；DONE有效项目已完成；HISTORY保留归档和取消。dueWeek按指定日所在周一至周日筛选计划结束日，overdue=true仅有效未关闭且planEnd早于业务日。行含NodeItem、projectName/projectStatus/moduleOwnerId、flags、交付率兼容progress。
- bugs参数：scope=OPEN|DONE|HISTORY（默认OPEN）、status=TODO|DOING|DONE、assigneeId（默认本人）、projectId、q、overdue=false、page、size。仅kind=BUG；OPEN有效项目、来源未取消且Bug未解决，来源DONE仍可OPEN；DONE相同项目/来源范围内已解决；HISTORY包括归档/来源取消历史。overdue仅上述OPEN且dueDate早于业务日。行含Task、projectId/projectName/projectStatus、nodeName/nodeStatus（业务来源）、origin各字段与noteCount；nodeId保持存储归属。
- USER仅其仍是成员的项目，VIEWER/ADMIN全局可读。显式无权projectId返回403，不存在404，非法枚举/ID/超过200字搜索返回400；q按名称/所属项目/来源名称包含匹配，百分号、下划线、感叹号均按字面搜索。指定其他负责人/执行人不会扩大项目读取范围。
- 交付与Bug列表按延期优先、计划/截止日、ID稳定排序。旧workspace/tasks与workspace/work-items保持兼容，当前默认工作流使用本节接口。
- /workload.people新增deliveryOpenCount/deliveryDoingCount/deliveryOverdueCount/deliveryWeekDueCount/openBugCount/overdueBugCount。范围仅有效项目，与上述交付/Bug读取筛选完全一致；本周交付指未完成且计划结束日在选定自然周内。旧任务和人天字段保留原历史口径，不与新交付数混合。聚合查询按负责人分组，前端无需逐项目/逐人取详情拼接。

## 4. 业务规则（后端实现要点）

### 4.1 延期/临近自动判定（每次查询按业务日期计算）
```
overdue = (status ∈ {NOT_STARTED, IN_PROGRESS}) AND (plan_end < 今天)
临近    = (status ∈ {NOT_STARTED, IN_PROGRESS}) AND (0 ≤ plan_end - 今天 ≤ 3) AND NOT overdue
```
- `overdue` 不落库。查询和聚合按同一业务日期计算，跨午夜立即生效；数据库对 `status, plan_end` 建索引。
- 延期原因提交后通知 PM 和模块负责人；未提交原因时工作项详情提示负责人。重复提交相同内容不重复通知。

### 4.2 功能交付与聚合

- 工作项是最小交付单元。只有DONE为100，未开始/进行中/已取消为0；不再从任务完成率、资料数量或进行中状态推测百分比，也不读写旧nodes.progress列。旧手动进度接口仍返回4090，隐藏于OpenAPI。
- 模块/项目交付率=已完成工作项数÷未取消工作项总数，四舍五入，有未交付项时最高99%。stats.total为未取消工作项总数，stats.done为已交付；模块新增totalWorkItems/doneWorkItems，nodeCount保留含取消的旧总数。
- 完成工作项由其管理者确认，不再校验旧任务全部完成。新增/修改Bug不更改功能DONE状态；Bug独立状态和交付状态各自统计。原任务/工时/文件数据不重写，已发布周报保留原JSON快照。
- 工作项状态及Bug状态采用节点/任务行锁，expectedStatus防并发；旧分流Bug存储与来源节点按id顺序锁定后再锁任务，重新检查写权限与当前状态。所有业务写保留项目成员、有效账号、职务、归档检查。

### 4.3 默认负责人继承链（创建时）
```
新建模块工作项 → owner = 所属模块 owner（可改派）
新建项目级工作项 → owner = 当前 PM（缺失时用操作人，可改派为项目内任意有效成员）
新建任务 → assignee = 所属工作项 owner（可改派）
```

## 6. 安全与扩展预留

- 接口 #17-#27、#68 均需校验"项目内职务"（PM 全权 / 模块负责人管本模块 / 工作项负责人管本工作项 / 执行人仅自己的任务 / 项目级工作项由 PM 或工作项负责人管理）；VIEWER 一律只读。
- 项目 `planStart` 必填，`planEnd` 可空。阶段性目标直接属于项目，目标日期须位于项目范围内；缩短项目日期范围时不得排除已有阶段性目标。模块不包含阶段日期。
- `modules.parent_id` 仅预留多级模块字段，v1 不开放嵌套；多负责人、IM/邮件通知、燃尽图均不属于 v1。
- v1 单体部署；如后期需独立通知服务，通知逻辑已收敛在 #4.4 的 5 个触发点，便于抽取。
