# 用户体验走查与简化建议

日期：2026-10-26。状态：现状诊断与待确认建议，尚未变更产品契约或功能。

## 1. 结论

现在的产品把“项目、模块、工作项、任务分别怎么维护”展示得较完整，却没有把“用户每天怎么把工作往前推进”组织起来。用户需要先理解层级、找到页面、辨认权限，再开始处理工作；统计和表单的数量超过了行动指引。

建议把产品主线明确为：**让小团队知道谁在什么时候交付什么，哪里卡住了，下一步由谁处理。**

这意味着成员首先看到自己的任务，负责人首先看到交付与待处理风险，管理者首先看到项目交付状态。项目、模块、工作项、任务仍保持现有归属，界面围绕用户行动组织入口。

## 2. 体验范围与证据边界

- 使用本地真实前后端，分别以演示项目经理、普通执行成员、只读管理者登录。
- 实际查看项目总览、项目时间线、项目设置、模块列表、模块工作页、工作项详情、任务详情、任务看板、周报、人员负载与通知中心；打开新建任务和提缺陷表单。
- 在右侧浏览器默认约 929px 宽度与 1440px 桌面宽度检查布局。时间线重叠与无日期刻度在两种宽度都存在；标题挤压和表格横向操作成本在窄窗口更严重。
- 项目文档、创建项目后的跳转、风险写入和缺陷分流规则通过当前源码核对。未实际新建项目、提交缺陷、修改状态、上传文件、发布周报、审批或删除业务数据。
- 本机原先未监听 5173/58080；为体验启动已有 Vite 和后端 jar，后端健康检查为 `UP`，前端 HTTP 200。本次后端启动关闭 Flyway 自动迁移，未执行种子导入。
- 演示项目排期主要在 2025–2026 年初，体验日期已是 2026-10-26。因此不把“延期数量多”当作产品缺陷；诊断针对信息组织、导航与处理能力。使用已有 jar，不把本轮走查视为源码重新构建后的完整回归。

## 3. 按用户目的回放

| 用户现在想做的事 | 当前路径和体验 | 简化后的目标 |
|---|---|---|
| 成员：找到今天要做的工作 | 登录进入项目总览；项目卡片 → 时间线 → 工作项 → 任务详情，已知位置时需 3 次点击；经模块列表定位则更长。没有跨项目“我的任务”或按本人筛选 | 首页直接列出指派给自己的未完成任务，可一键开始/完成，点击任务打开详情 |
| PM：安排一项交付 | 先区分模块工作项和项目级工作项；模块工作项需进入模块页创建，跨模块工作项则在时间线/模块列表创建 | 项目里统一“新建工作项”，在表单里选择功能模块或跨模块，并继承已有负责人默认值 |
| PM：搭好一个新项目 | 源码中创建后跳项目设置；成员、阶段目标、审批、模块混在长页内，创建模块在页面底部 | 创建后显示明确的下一步：邀请成员 → 建立首个工作项 → 拆任务；模块分组按实际需要维护 |
| 负责人：说明卡在哪里 | 工作项详情有延期标签，但没有延期原因入口；受阻按钮提交固定原因 | 在风险卡中看到原因，并能填写/更新说明；管理者从风险列表直接进入处理 |
| 成员：在看板上推进任务 | 看板能下拉改状态，不能直接打开任务详情、写记录或查看附件；需回工作项再找任务 | 列表和看板共用任务详情入口，切换视图保持当前项目、工作项和筛选条件 |
| 管理者：判断项目交付是否可控 | 首页有进度百分比和风险数量，点进去主要是条块；缺少交付日期、下一阶段目标和具体待处理风险的集中呈现 | 项目概览先回答交付什么、下一个日期、谁负责、哪里受阻，再展开排期和统计 |

同一用户可以兼任 PM、模块负责人和执行人。建议按当前工作与项目职务呈现内容，不新增互斥的全局身份。

## 4. 优先修复的操作断点

### P1-01：项目上下文不稳定，侧栏会指错项目或消失

**浏览器复现：**项目 1 → 工作项 106 后，侧栏链接变成 `/projects/106/...`；点击“项目设置”进入 `/projects/106/settings`，页面失去正确项目内容。进入 `/projects/1/modules/2` 时，整组“当前项目”导航消失。

**原因：**`frontend/src/App.vue:10` 把 `route.params.id` 一律当项目 ID；工作项页的 `id` 是工作项 ID，模块详情使用的是 `projectId`。

**影响：**用户无法确信自己在什么项目里，也无法稳定返回周报、文档和设置。应先统一项目上下文，再调整导航；工作项页从服务端返回的 `projectId` 取得所属项目。

### P1-02：核心时间线不能可靠回答“什么时候交付”

**浏览器复现：**同一模块内有日期交叉的工作项画在同一高度，条块与标题互相覆盖；1440px 宽度仍存在。没有可读日期轴、今日线或图例；负责人主要只显示在模块名称下，工作项条上没有自己的负责人。

**原因：**`frontend/src/styles.css` 的 `.timeline-bar` 全部固定 `top:22px`，没有分行排布；`TimelineView.vue` 只有按日期比例定位的条块，没有刻度组件。

**建议：**先提供清晰的工作项列表；保留时间线为排期视图，并补日期刻度、重叠分行、今日定位、负责人和状态说明。新增“今日”相关判断继续遵循服务端业务日期与时区契约。

### P1-03：普通成员看到自己无权执行的管理按钮

**浏览器观察：**只负责具体任务的普通成员，在工作项详情仍看到“完成工作项”“标记受阻”；周报草稿中仍看到“保存说明”“发布周报”。

**源码核对：**`NodeDetailView.vue:66` 主要按 `!readOnly` 展示状态与受阻按钮；`WeeklyReportView.vue` 主要排除 VIEWER。后端 `WorkService` 要求工作项管理权限，`ReportingService` 要求 PM/ADMIN，服务端授权仍存在。

**影响：**用户把可见按钮理解为可用操作，点击后才会发现无权限。本次未实际提交这些写请求。应统一按现有职务、归档状态与关闭状态呈现操作入口。

### P1-04：异常有标记，却缺少有用的反馈入口

**浏览器观察：**延期工作项详情没有填写延期原因的入口，也没有集中展示已有延期说明；周报能够看到已有原因，但不能从该行直接进入工作项处理。

**源码核对：**后端已有 `overdueReason`；前端 `NodeDetailView.vue:52` 的 `block()` 固定提交“进展受阻，待负责人补充处理”，没有先收集真实原因。

**影响：**风险提醒无法帮助负责人说明问题，也无法帮助 PM 判断需要协调什么。优先补通现有风险说明能力，复用现有接口和权限。

### P2-05：完成条件只在提交时解释

工作项尚有未完成任务时，详情仍展示可点击的“完成工作项”。源码中后端会拒绝并返回剩余未完成任务数；界面没有预先解释条件。已取消工作项还可能显示受阻入口。

建议操作区直接说明“还剩 3 个任务”，未满足条件时给出明确提示；符合条件时展示清楚的收尾动作。保留工作项显式完成与既有进度派生规则。

## 5. 造成繁琐的产品组织问题

### P1-06：首页没有个人工作的入口

三种角色都进入项目卡片列表。普通成员与 PM 的首页内容基本相同，只读管理者主要少了新建按钮。人员负载有“未完成任务”数字，却没有点击后查看对应任务的能力。

建议首页成为“我的工作”：进行中、待开始、已逾期，以及本人负责工作项的风险和待办审批。项目总览保留为项目入口。任务数量应能展开成任务清单，清单中的任务应能直接打开。

### P2-07：项目、模块、工作项、任务同时成为导航负担

“我要让某人在某天做完某件事”被拆散在不同层级的页面里；模块工作项与跨模块工作项使用不同创建入口，用户必须先学会归属规则。阶段性目标和工作项又都涉及交付日期，页面缺少贴近场景的例子。

建议持续使用现有术语，并配简短例子：项目是“商城上线”，模块是“订单支付”，工作项是“完成支付接入”，任务是“实现回调验签”；阶段性目标是项目的关键交付日期。创建入口收敛，归属在上下文中带出或选择，服务端仍校验权限。

### P2-08：首次创建就展示过多补充字段

实际打开新建任务，有 9 个字段：名称、描述、任务情况、处理方式、类型、关联工作项、执行人、截止日期、计划人天。虽然多数可选，视觉上都在要求用户做决定；“描述、任务情况、处理方式”语义接近。

建议默认只展开“做什么、谁来做、什么时候完成”，继承现有执行人默认值；其他放入“更多信息”。任务情况、处理方式、记录优先在执行过程中按需要补充。这里是展示简化建议，不代表删除现有字段或更改必填契约。

### P2-09：项目设置承担了过多日常工作

基本信息、成员、阶段目标、模块变更审批、模块管理位于同一长页。模块列表本身没有新建模块入口，PM 必须转到设置寻找；审批也藏在配置页面中。

建议模块页提供已有模块管理操作；待审批事项从工作台与项目概览直达。阶段性目标继续在项目设置维护、在项目概览/时间线呈现，遵循当前约定。设置页可按基本信息、成员、阶段目标等分区减少滚动。

### P2-10：文件与交付物的关系解释成本高

工作项页同时显示任务、交付物、文档与文件，任务弹窗又有附件。文件已有全项目汇总能力，但没有固定项目导航入口；“交付物已提供”和“文件已上传”之间仍需用户自己关联理解。

建议默认突出任务与风险，交付物、文件使用带数量的页签或折叠区；在交付物内提供明确的关联文件流程，复用现有附件体系。项目固定导航提供文档入口。保留交付物清单不参与进度、不阻断工作项完成的决定。

### P2-11：周报展示重点与当前使用方式脱节

周报第一屏以“工时概览”为主，而当前产品已取消工时录入口；历史周报只显示周和状态，源码没有点击切换历史报告的动作。普通成员还会看到维护草稿的操作入口。

建议默认先显示本周完成、延期受阻、后续交付和说明，工时保留历史参考位置；历史报告点击后切换到对应周，发布权限按 PM/ADMIN 控制。保留历史快照与工时统计契约。

### P2-12：提缺陷隐藏了接收前提

表单只有“标题、问题描述、任务情况、关联工作项”。源码表明，不关联或关联已结束的工作项时，需要已开启的项目级缺陷修复工作项，否则提交才返回 409；表单打开时没有接收状态说明，描述和任务情况又有重复理解成本。

建议先显示当前接收情况，缺少接收工作项时明确下一步由 PM/ADMIN 处理；给成员的说明使用“谁会接收这个问题”。本次未实际提交或制造缺陷数据，不据此声称完成缺陷流程回归。

### P3-13：语言、布局和空状态继续增加理解成本

- 工作项状态显示 `IN_PROGRESS / DONE / NOT_STARTED`，成员表显示 `USER / MEMBER / PM`；登录页仍强调当前已隐藏录入口的“工时”，部分演示通知内容仍称“节点”。
- 在约 929px 宽的侧栏浏览器中，页头同时排列多个按钮，把项目标题挤成多行；任务表右侧操作需要额外横向查看。
- 空项目只提示“项目尚无模块和工作项”，没有按职务告诉用户下一步；项目总览的延期数字也不能直接筛出异常。
- 通知中心没有全局未读计数，通知本身主要落到工作项而非具体任务；日期直接显示 ISO 字符串。

建议复用已有中文标签、时间格式化、附件与页面骨架；新增公共映射或上下文封装时登记复用库。空状态给出与职务匹配的下一步；头部操作区允许换行，常用动作优先显示。

## 6. 推荐的使用主线

| 场景 | 界面首先回答的问题 | 主要动作 |
|---|---|---|
| 每天开始工作 | 我负责什么、什么快到期、有什么卡住 | 开始任务、更新进展、完成任务 |
| 进入一个项目 | 要交付什么、下一关键日期、哪些事项需要处理 | 新建工作项、处理异常、查看排期 |
| 安排具体交付 | 谁负责、何时完成、分成哪些任务 | 保存工作项后直接拆任务 |
| 周会或向上汇报 | 本周完成了什么、风险是什么、下一步交什么 | 查看周报，PM 补充说明并发布 |

建议项目内保持稳定导航：概览、工作项、时间线、文档、周报、设置。模块作为工作项的分组与管理入口呈现；首页的具体命名与导航项数量在实现前再收敛。阶段性目标仍属于项目，功能模块仍不承载阶段日期。

## 7. 实施顺序与验收建议

### 第一批：修复现有路径

1. 正确传递项目上下文，修复工作项和模块详情侧栏。
2. 按职务与生命周期控制操作，完成条件提前说明。
3. 补通延期说明、受阻原因的展示与编辑。
4. 列表与看板共享任务详情入口；历史周报可点击读取。
5. 统一中文状态，处理窄窗口头部与任务操作列。

验收：从任意工作项/看板都回到所属项目；进入模块详情导航保持；普通成员不出现无权管理的按钮；负责人能填写具体受阻原因和延期说明；读取历史周报显示对应周的快照。

### 第二批：围绕日常行动收敛入口

1. 增加跨项目“我的任务/我的工作”入口。
2. 项目入口先呈现交付与可处理风险，再提供排期视图。
3. 统一工作项创建入口，任务表单默认只展开核心字段。
4. 将模块管理和待审批事项放到用户找得到的工作位置。

验收：成员登录即可看到自己的未完成任务，一次点击打开任务；PM 从项目内一个统一入口创建模块工作项或跨模块工作项；角色兼任时能同时找到个人任务与管理待办。

如新增跨项目任务汇总接口，必须按账号可读项目和任务指派过滤，在服务端完成筛选与分页；不要让浏览器逐个拉取所有项目、模块和工作项拼装清单。相应更新接口设计、OpenAPI 类型与复用登记。

### 第三批：改善排期与补充信息

1. 时间线补刻度、今日定位与防重叠布局。
2. 交付物与文件按需要展开，关联流程清晰。
3. 周报突出完成、风险与下一步；提缺陷在填写前说明接收状态。

验收：日期交叉的工作项均可辨认和点击；用户能指出每项交付的日期与负责人；能从风险数量进入具体问题，从任务进入相关记录和文件。

## 8. 本轮交付边界

以上顺序和界面方案属于建议，尚未经用户确认；不能覆盖 `PROJECT_MEMORY.md` 中现有实体、权限、日期、进度、交付物与周报决定。本轮只更新体验记录，不修改功能代码、API 或数据库，不涉及提交、合并和发布。文档无需运行 Maven/前端构建；上述浏览器观察也不能替代后续实现后的角色路径与写操作验证。
