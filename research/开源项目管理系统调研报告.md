## 2. 重点产品深析：里程碑/阶段—任务—负责人模型与交互

### 2.1 Plane（makeplane/plane）— 最现代的「节点化」设计

**数据模型**（docs 结构：[docs.plane.so](https://docs.plane.so/llms.txt)）：
- 层级：`Workspace → Project → {Cycles, Modules, Views} → Issues（父子层级）→ Sub-issues`，另有 Pages（文档）与 Intake（想法收集，`Project` 级视图）。
- **Cycle（周期）**：即冲刺，带起止日期；周期页有进度分析（燃尽图、速度图），展示每个 issue 在周期内的状态变化——把「时间盒」作为一级进度节点。
- **Module（模块）**：跨周期的功能模块/特性分组（对应 epic/feature），字段含 **Lead（模块负责人）**、Members、起止日期、状态（backlog/planned/in progress/paused/completed/cancelled）与**自动进度**（关联 issue 完成占比）。这是「模块+模块负责人」最直接的实现样板。
- **Issue**：5 类状态组（backlog/unstarted/started/completed/cancelled，可自定义状态名但映射到组）、**多 assignee**、estimate 点数、起止日期、labels、relations（blocking/blocked_by/duplicate/related）、评论与活动流。
- **Views（视图）**：List / Kanban / Calendar / Spreadsheet / **Gantt**（支持依赖箭头、拖拽排期、关键路径高亮）。视图与数据分离，同一批 issue 可多种视角。

**交互**：看板拖拽改状态→模块/周期进度自动聚合；甘特视图拖拽建依赖；周期页看燃尽。发布节奏每周一次，社区非常活跃（[2025 年底 50k+ star 代码审计文章](https://dev.to/rohit_sriram_970bf595b17b/i-scanned-plane-50k-stars-for-bugs-found-32-zero-false-positives-1png)）。

**借鉴点**：`Cycle（时间节点）+ Module（模块节点，带 Lead）+ Issue（任务，多负责人）+ Views（多视图）`四件套是最接近我们需求的开源实现；模块的 Lead/Members/Status/自动进度字段可直接照抄。

**短板**：AGPL-3.0；部署需 6+ 容器（web/api/worker/beat/redis/postgres/minio）；企业功能（SSO 等）在付费计划；自定义状态受 5 个状态组约束。

### 2.2 OpenProject — 经典 PM 的「类型打标 + 层级」模型

**数据模型**：一切皆 **Work Package（WP）**；用 **Type** 区分语义：Task、**Milestone**、**Phase**、Bug、Feature、Epic、User story、Meeting，均可自定义类型/状态工作流/自定义字段（[官方文档](https://www.openproject.org/docs/user-guide/work-packages/)）。
- 关键字段：subject、type、status、priority、**assignee（单一 Responsible）**、accountable、起止日期、预估工时、**% done**、**parent（无限层级）**、relations（relates/blocks/precedes/follows/part of）、**version（发布/里程碑节点）**、自定义字段。
- 视图：Table（内嵌甘特）、Board（看板）、Calendar、Backlogs（Scrum）、Team planner、**Work breakdown（层级分解）**、**Roadmap（按 Version 的时间轴）**、双栏分屏、Meetings。
- 甘特：依赖箭头、拖拽排期、基线对比、里程碑菱形、进度线。
- 权限：**基于角色的权限矩阵**（项目成员+全局角色+自定义角色），assignee 单一，这是「节点负责人」权限联动的最强实现。

**交互**：Phase 类型 WP 下挂子任务形成「阶段—任务」树；Roadmap 视图把各 Version（发布节点）画在时间轴上；甘特拖拽直接改 WP 起止与依赖。

**借鉴点**：`Phase`（阶段节点）与 `Milestone`（里程碑节点）都是 WP 的一种 type，天然继承 assignee/状态/依赖/父子——「节点与任务同构」的设计让权限和视图实现统一。Version 作为「交付节点」与任务 N:1 关联。

**短板**：Rails 单体 + 传统 UI（v14 起用 Primer/Hotwire 改进中）；部署与学习成本高；甘特基线等高级功能在 EE；「模块负责人」需自建自定义字段或角色实现，不如 Plane 的 Module.Lead 直观。

### 2.3 Taiga — 敏捷双模式的「层级 + 时间盒」模型

**数据模型**（scrum/kanban 双模式）：
- 层级：**Epics → User Stories（可挂 Tasks）→ Tasks**；另含 Issues（缺陷）、Wiki、**Milestones（冲刺）**（起止日期）、自定义属性。
- **Backlog → Sprint backlog**：产品待办拖入冲刺；Sprint 页提供 **Taskboard（按 Story 泳道）**、**燃尽图**、**速度**。
- **Story Points 可按角色分别估算**（role points）——不同角色对同一 story 独立估点，是多角色协作的独特设计。
- 负责人：story/task **单一 assignee** + watchers + due date；Kanban 模式支持 WIP 限制与泳道。
- 权限：角色权限矩阵、项目成员管理。

**交互**：拖拽 backlog→sprint 规划迭代；Taskboard 泳道拖卡流转；燃尽图闭环。**无原生甘特、无路线图时间轴**（epic 仅列表视图）——这是它的最大缺口。

**现状**：社区版维持性更新（8.0.5，2024），原核心团队创立 [Tenzu](https://tenzu.net/en/who-are-we/)（[NLnet 资助](https://nlnet.nl/project/Tenzu/)），FOSDEM 2026 谈开源可持续性。仍是理解「冲刺时间盒 + 层级任务 + 单负责人」的教科书案例。

**借鉴点**：Sprint/Milestone 作为独立时间盒实体 + 层级容器（Epic→Story→Task）+ 单负责人清晰问责；燃尽/速度是「节点进度可视化」的成熟范式。若我们要做「节点负责人」，Taiga 证明单 assignee + 角色权限足够简单清晰。

## 3. 专做「路线图 / 甘特 / 里程碑」的轻量开源工具

| 工具 | 类型 | 「进度节点」建模方式 | 借鉴点 |
|---|---|---|---|
| **[GanttLab](https://github.com/ganttlab/ganttlab)**（≈1k star，Vue.js） | 只读甘特可视化 | 直接消费 GitHub/GitLab API：**milestone（带日期）即进度节点**，issue 的 start/due date 即任务条；label/负责人映射到条样式；无持久化、无写入 | 「节点可视化」的最小可行范本：不动数据，只做时间轴渲染，立刻有价值 |
| **[GanttProject](https://github.com/bardsoftware/ganttproject)** | Java 桌面甘特 | 任务+依赖+资源+**里程碑**；MPXJ 支持导入导出 MS Project | 传统 PM 心智：里程碑是零工期任务，占位时间轴 |
| **[Frappe Gantt](https://docs.frappe.io/gantt/introduction)** | JS/SVG 甘特库 | 任务 = {start, end, progress, dependencies}；拖拽改期、进度条填充、依赖连线 | **最小数据模型**：节点就是带起止日期的任务，progress 字段直接表达完成度；适合起步 |
| **GitHub Projects Roadmap layout** | 内置路线图视图 | 用 Start date / Target date / Iteration 字段渲染时间轴；可按 Milestone/自定义字段分组；进度=子 issue 完成度（[文档](https://docs.github.com/ja/issues/planning-and-tracking-with-projects/customizing-views-in-your-project/customizing-the-roadmap-layout)） | 字段驱动：任何有日期字段的条目都能上时间轴；按节点分组的交互很自然 |
| **GitLab Roadmap**（Ultimate） | 内置路线图 | Epics 的 start/due date 时间轴 + milestones 标记 | epic 作为路线图条目、milestone 作为刻度节点 |
| **OpenProject Roadmap 视图** | 内置 | 按 Version（发布节点）横向时间轴 | 交付节点主导的路线图视角 |
| **Huly Planner / Linear Projects（商业参考）** | 内置路线图 | Projects 下挂 Milestones（日期+状态），进度=issues 完成比例自动计算；Linear 的 Project+Milestone 是「节点化进度」最佳商业参照 | Milestone 有独立状态机和负责人，项目进度条自动聚合 |
| **Leantime Goals→Milestones** | 内置三层 | Goals（蓝图）→ Milestones（状态+进度）→ To-dos | 非技术用户友好的「节点树」 |
| **[Tenzu](https://tenzu.net/)** | 新项目（早期） | Taiga 原团队出品，Django+Angular，NLnet 资助 | 关注其是否会补上 Taiga 缺失的路线图能力 |

## 4. 总结：『进度节点化 + 模块/节点负责人分配』的行业实现方式与可借鉴点

### 4.1 术语对照（同一概念的不同叫法）

| 概念 | 各家术语 |
|---|---|
| 时间盒节点（迭代） | Sprint（Taiga/Jira）、**Cycle**（Plane）、Iteration（GitHub） |
| 目标/阶段节点 | **Milestone**（GitHub/GitLab/Jira/OpenProject/Linear）、**Phase**（OpenProject Type）、Goal（Leantime/Linear） |
| 功能模块容器 | **Module**（Plane）、Epic（Taiga/Jira/GitLab）、Feature（OpenProject Type）、Component（Jira 字段） |
| 交付/发布节点 | Version/Release（OpenProject/Jira）、Release（GitLab） |
| 任务 | Issue/Task/Work Package/To-do/Card |

### 4.2 数据模型三大流派

1. **类型打标流（OpenProject/Jira）**：节点与任务是同一种工作项（WP），用 type 区分 Phase/Milestone/Task；统一继承 assignee/状态/依赖/父子关系。→ 实现统一、灵活，但概念重。
2. **独立实体流（GitHub/GitLab milestone、Taiga sprint、Plane Cycle）**：节点是独立实体，与任务 N:N 关联，**进度由关联任务状态自动计算**。→ 轻量直观，是「进度节点化」的主流做法。
3. **层级容器流（Taiga Epic→Story→Task、Plane Module、Vikunja 无限子任务、Huly 父子 Issue、Leantime Goals→Milestones→To-dos）**：树形嵌套，父节点=模块/阶段，子节点=任务，父节点进度=子树聚合。

### 4.3 负责人分配模式

- **单负责人**（Taiga、OpenProject 的 Responsible、Kanboard、Wekan）：问责清晰、权限简单。
- **多负责人**（Plane、Vikunja、Huly、GitHub Issues）：协作友好，但「责任人」需额外区分。
- **模块/节点负责人**的实现惯例：
  - Plane：Module 实体上设 **Lead + Members** 字段；
  - OpenProject：Phase WP 的 assignee（Responsible）+ accountable 字段；
  - Jira：Epic 的 assignee + Component lead；
  - Linear：Project lead + Milestone 无独立 owner（归 Project）。
  - 权限联动：项目角色矩阵（OpenProject 最强）决定谁能看/改节点；成员列表控制可见性。

### 4.4 界面交互套路

1. **甘特/时间轴**：拖任务条改起止、拖连线建依赖、里程碑菱形、关键路径高亮、进度条填充（Plane Gantt、OpenProject、Frappe Gantt、GitHub Roadmap）。
2. **看板拖拽改状态 → 节点进度自动聚合**（Plane Module/Cycle、Linear Project 的进度条）。
3. **节点详情页**：状态、日期、负责人、关联任务列表、完成百分比（GitHub milestone、Leantime、Linear）。
4. **迭代闭环**：燃尽图/速度图（Taiga Sprint、Plane Cycle Analytics、GitHub Insights）。
5. **路线图总览**：时间轴按节点分组（GitHub Roadmap layout、OpenProject Roadmap、Huly Planner、GitLab Roadmap）。

### 4.5 给我们产品的可借鉴点（要点）

1. **数据模型建议**：节点（里程碑/阶段/模块）设为**独立实体**，任务通过 parent/link 关联；节点字段集 = {名称、起止日期、状态机(planned/active/blocked/done)、owner(s)、members、描述、自定义字段、进度(自动聚合+可手动锁定)、依赖(blocks/follows)}。这是 GitHub milestone + Plane Module + OpenProject Phase 的并集。
2. **负责人双层设计**：节点 owner（模块负责人，管可见性/编辑）+ 任务 assignee（执行人）；初期建议单 owner 多 assignee，参考 Plane Module.Lead + Issue.multi-assignee。
3. **进度计算**：任务状态加权或 story points 加权自动聚合；支持「手动进度覆盖」；依赖 + 关键路径用于延期预警。
4. **三件套视图**：甘特（拖拽+依赖+里程碑菱形，可用 Frappe Gantt 起步）+ 看板（状态流）+ 路线图时间轴（按节点分组）；GanttLab 证明「只读时间轴」也能先出价值。
5. **部署/技术选型参考**：轻量起步可学 Vikunja（单二进制）或 Kanboard（插件化）；要现代栈学 Plane（Next.js+Django）或 Huly（Svelte+TS）；避免 Focalboard（已停维）、Taiga 社区版（维持期）作基座。
6. **差异化机会**：现有产品中「节点负责人」要么缺（GitHub/GitLab milestone 无 owner）、要么隐式（OpenProject 用 type+assignee）、要么只在商业产品完整（Linear）。**「节点/模块负责人」作为一等公民 + 轻量自托管** 是明确的市场空位。
